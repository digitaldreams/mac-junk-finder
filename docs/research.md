# Count allocated bytes, skip trees, label tiers

JunkFinder should copy the design of Mole's open-source rule set, the most rigorous one available. That means three tiers instead of one "junk" bucket: **Junk** (rebuilds itself), **Review** (large, but may be the only copy of something) and **Never shown** (user data, credentials, cloud folders, toolchains). Every size it prints should be **allocated bytes** (`totalFileAllocatedSizeKey`), never logical size. One choice fixes three traps at once: sparse VM disks, compressed files and iCloud dataless files would otherwise show up as gigabytes of fake junk. Hard links need a (device, inode) dedup set. APFS clones and snapshot-pinned blocks still make even allocated size overstate what deleting frees, so the output has to say "up to". Staleness should come from modification date (and the newest child's date for folders) plus "date added" in Downloads. atime on APFS records only the first read after a write, and Spotlight's last-used date is missing on almost every large file. Without Full Disk Access a terminal-launched CLI gets a silent `EPERM` on `~/.Trash`, Mail, Safari and Messages, and no prompt ever appears. Reading Downloads, which the installer category needs, can show a one-time prompt naming the terminal app. So JunkFinder should scan without FDA by default, skip protected and cloud trees before walking into them, report each skipped area by name, and offer an explicit `--check-access` probe. On speed, the biggest gain comes from not walking cloud, Photos, Mail, container and VM trees, and from not descending into a folder once it matches a rule. A faster syscall matters less. A synchronous `FileManager` URL enumerator with prefetched keys is good enough for v1. The concrete rule table, API list, skip list, FDA flow, caveats, tests and open questions follow.

## Real cleaners split junk into three tiers, and only one is safe

Commercial and open-source cleaners differ more in how careful they are than in which paths they look at. CleanMyMac's System Junk covers user and system caches, logs, language files, Xcode junk, iOS backups and document versions. It decides what is safe through a proprietary "Safety Database" and refuses to auto-select the riskiest items: **"CleanMyMac never selects the most recent backup for removal automatically"**, and it doesn't pre-select Xcode module caches or archives ([MacPaw](https://macpaw.com/support/cleanmymac/knowledgebase/system-junk-cleanup-list); [MacPaw Safety Database](https://macpaw.com/support/cleanmymac-x/knowledgebase/safety-database)). OnyX cleans system, user and Internet caches and logs, and its exact path list is not published ([Titanium Software](https://titanium-software.fr/en/onyx.html)). DaisyDisk has no junk categories at all. It visualises usage and shows "purgeable" space, which is mostly local snapshots, swap and temporary files ([DaisyDisk](https://daisydiskapp.com/guide/purgeable-space)). Pearcleaner's Development view hard-codes about 20 toolchain cache paths for the user to browse and delete by hand, not to flag automatically ([Pearcleaner source](https://github.com/alienator88/Pearcleaner/blob/7724df7111bff82ae243301cf701992ef05ecf19/Pearcleaner/Views/DevelopmentView.swift#L1606-L1720)).

Mole is the one to study, because its code states its rules and its reasons. It has three tiers: an auto-clean list, a **review-only list reported at ≥1 GB and never deleted**, and a protected list ([Mole user.sh](https://github.com/tw93/Mole/blob/e6b990998c0d0bbcba4e0fcaa8e7b77e0e327c22/lib/clean/user.sh#L3404-L3593)). The review tier is close to JunkFinder's "big & stale" category, and Mole explains why it exists: "100GB of last month's phone backup is the only copy of that phone, and 100GB from a device sold two years ago is dead weight." mac-cleanup-py shows the opposite approach. It deletes `~/Library/Caches/*` wholesale and removes every iOS backup and Xcode archive outright ([mac-cleanup-py](https://github.com/mac-cleanup/mac-cleanup-py/blob/c8fbdb402dc04cb4e4893b6f752a827470a071b0/mac_cleanup/default_modules.py#L71-L82)). JunkFinder should not copy that.

Two more lessons carry over even though JunkFinder never deletes anything. First, Mole uses each tool's own cleanup command rather than raw deletion: `brew cleanup --prune=30`, `npm cache clean --force`, `pnpm store prune`, `go clean -modcache` and `xcrun simctl delete unavailable`. Its comment says "Native simctl owns simulator state… never bypass it with direct directory removal" ([Mole dev.sh](https://github.com/tw93/Mole/blob/e6b990998c0d0bbcba4e0fcaa8e7b77e0e327c22/lib/clean/dev.sh#L2880-L2905)). JunkFinder should print that command next to each finding instead of implying `rm -rf`. Second, Howard Oakley points out that macOS already purges caches through `deleted` (CacheDelete), and that "the caches in question here aren't old, normally, they're the current ones in active use." Wiping them mostly costs performance ([Eclectic Light, Sept 2026](https://eclecticlight.co/2026/09/02/caches-and-purging-in-macos-tahoe/)). Flushing caches frees much less than deleting snapshots or evicting iCloud files ([Eclectic Light](https://eclecticlight.co/2023/09/22/will-flushing-caches-free-up-disk-space/)). A list-only tool is still dangerous when its labels are wrong, because users act on them. The consequence line on each Review item ("only copy of a device backup", "re-downloads N GB") is the main safety feature JunkFinder can offer.

## Path by path: what is safe, what needs review, what is never junk

**Caches and logs are mostly safe, with a deny-list.** Mole flags every child of `~/Library/Caches` but skips any cache whose owner process is running. Its reason: deleting an open SQLite cache "can send the owning helper into a loop writing to unlinked files until the volume fills" ([Mole SECURITY_AUDIT](https://github.com/tw93/Mole/blob/e6b990998c0d0bbcba4e0fcaa8e7b77e0e327c22/SECURITY_AUDIT.md)). A few children are not disposable. `CloudKit*`, `com.apple.FontRegistry*` and `com.apple.[Ss]potlight*` are on Mole's hard-safety list because removing them "breaks macOS search, font rendering and iCloud sync rather than costing a rebuild". `pypoetry/virtualenvs` "holds live interpreters every Poetry project points at". Deleting renv's cache leaves project libraries dangling ([Mole base.sh](https://github.com/tw93/Mole/blob/e6b990998c0d0bbcba4e0fcaa8e7b77e0e327c22/lib/core/base.sh#L198-L220)). `com.apple.bird` and `com.apple.CloudDocs*` are iCloud Drive daemon state ([Mole protection data](https://github.com/tw93/Mole/blob/e6b990998c0d0bbcba4e0fcaa8e7b77e0e327c22/lib/core/app_protection_data.sh#L553-L554)). Mole whitelists `com.apple.finder`, Playwright browsers, JetBrains caches and Ollama models by default, since they are expensive to rebuild ([Mole base.sh](https://github.com/tw93/Mole/blob/e6b990998c0d0bbcba4e0fcaa8e7b77e0e327c22/lib/core/base.sh#L173-L187)). Logs in `~/Library/Logs` older than **7 days** are safe; Mole uses 7 days for both logs and crash reports. Sequoia removed the old `periodic` housekeeping scripts, so nothing else prunes them ([Eclectic Light](https://eclecticlight.co/2025/01/28/please-dont-delete-your-logs/); [Mole base.sh](https://github.com/tw93/Mole/blob/e6b990998c0d0bbcba4e0fcaa8e7b77e0e327c22/lib/core/base.sh#L160-L161)). The unified log at `/var/db/diagnostics` is outside `~`, and Oakley calls cleaners that delete it "malicious". `~/Library/Saved Application State` is fine after **30 days**, at the cost of window restore ([Mole base.sh](https://github.com/tw93/Mole/blob/e6b990998c0d0bbcba4e0fcaa8e7b77e0e327c22/lib/core/base.sh#L160-L166)). Browser caches are safe only at the cache-subfolder level: Chromium's `Code Cache`, `GPUCache`, `ShaderCache` and similar, Firefox's `cache2`, and Safari's `~/Library/Caches/com.apple.Safari`. Never the profile ([Mole user.sh](https://github.com/tw93/Mole/blob/e6b990998c0d0bbcba4e0fcaa8e7b77e0e327c22/lib/clean/user.sh#L1976-L2122)).

**Developer junk splits along "download cache" versus "store that builds resolve from".** DerivedData, `Xcode/Products`, `CoreSimulator/Caches` and IB Support are rebuilt on the next build ([Mole app_caches.sh](https://github.com/tw93/Mole/blob/e6b990998c0d0bbcba4e0fcaa8e7b77e0e327c22/lib/clean/app_caches.sh#L170-L440)). The package-manager download caches are safe:

- Homebrew's `~/Library/Caches/Homebrew`. Brew already prunes downloads older than 120 days ([Homebrew manpage](https://docs.brew.sh/Manpage)).
- npm's `~/.npm/_cacache`. npm says "it should never be necessary to clear the cache for any reason other than reclaiming disk space" ([npm docs](https://docs.npmjs.com/cli/v10/commands/npm-cache)).
- Yarn's caches, pip's `~/Library/Caches/pip`, and `~/.cargo/registry/cache`. Since **Rust 1.88** Cargo auto-GCs downloads unused for 3 months ([Rust blog](https://blog.rust-lang.org/2025/06/26/Rust-1.88.0/)).

The stores are different. Mole keeps `~/.cargo/registry/src`, `index` and `git`, because rust-analyzer and offline builds read them ([Mole dev.sh](https://github.com/tw93/Mole/blob/e6b990998c0d0bbcba4e0fcaa8e7b77e0e327c22/lib/clean/dev.sh#L1320-L1348)). It treats `~/.m2/repository`, `~/.ivy2/cache` and `~/.nuget/packages` as review-only, because they are "the stores Maven, sbt and Ivy resolve dependencies from" ([Mole dev.sh](https://github.com/tw93/Mole/blob/e6b990998c0d0bbcba4e0fcaa8e7b77e0e327c22/lib/clean/dev.sh#L3024-L3031)). The pnpm store is shared through hard links, so the right fix is `pnpm store prune`, which "is not harmful and has no side effects on your projects" ([pnpm](https://pnpm.io/cli/store)). Gradle already cleans its own caches every 24 hours ([Gradle](https://docs.gradle.org/current/userguide/directory_layout.html)). Xcode Archives "hold the dSYMs that symbolicate crashes from shipped builds". They are Review with a date, never Junk ([Mole user.sh](https://github.com/tw93/Mole/blob/e6b990998c0d0bbcba4e0fcaa8e7b77e0e327c22/lib/clean/user.sh#L3484-L3489)). DeviceSupport folders take 1–3 GB per OS build and regenerate when a device connects, so the old ones are safe and the newest is not ([Donny Wals](https://donnywals.com/delete-old-simulators-and-device-support-files-to-free-disk-space)). Toolchains are never junk: `~/.cargo/bin`, `~/.rustup/toolchains`, `~/go/bin`, `~/.nvm`, `~/.sbt/boot` and `~/.stack/programs`.

**Project artifacts need a sibling marker file, not just a folder name.** Mole's purge list holds about 40 directory names, from `node_modules` and `target` to `.next`, `__pycache__`, `.build` and `Pods`. It guards the ambiguous ones: `vendor` counts only for Composer, `bin` only in a .NET context, and directories with recent or tracked "authored content" are protected ([Mole purge_shared.sh](https://github.com/tw93/Mole/blob/e6b990998c0d0bbcba4e0fcaa8e7b77e0e327c22/lib/clean/purge_shared.sh#L18-L103); [Mole project.sh](https://github.com/tw93/Mole/blob/e6b990998c0d0bbcba4e0fcaa8e7b77e0e327c22/lib/clean/project.sh#L580-L640)). The strongest signal is **`CACHEDIR.TAG`**, a regular file whose first 43 bytes are `Signature: 8a477f597d28d172789f06886806bc55`. The spec requires that it not be a symlink ([bford.info](https://bford.info/cachedir/)). Cargo writes it into `target/`, and pytest and uv write it too ([pytest](https://pytest.org/latest/_modules/_pytest/cacheprovider.html); [uv-fs](https://docs.rs/crate/uv-fs/0.0.52/source/src/cachedir.rs)). Its absence proves nothing, though. Cargo skips it when rust-analyzer created `target/` first, an issue closed as "not planned" ([cargo#14281](https://github.com/rust-lang/cargo/issues/14281)). The spec itself says tags are hints that could be planted, and that "System software should not automatically delete 'old' files in cache directories." So treat a valid tag together with a sibling `Cargo.toml` as high confidence, `Cargo.toml` plus the usual `debug/`/`release/` layout as medium confidence, and a bare `target` name as nothing. Maven also uses `target/`, and so do people for ordinary folders.

**Old installers are an extension list plus one content check.** Mole's installer finder looks for `.dmg .pkg .mpkg .iso .xip` to depth 2. It counts a `.zip` only if one of its first 50 entries is an `.app`, `.pkg`, `.dmg` or `.xip`, and it skips symlinks ([Mole installer.sh](https://github.com/tw93/Mole/blob/e6b990998c0d0bbcba4e0fcaa8e7b77e0e327c22/bin/installer.sh#L38-L125)). It also flags incomplete downloads (`*.download`, `*.crdownload`, `*.part`) that are not open ([Mole user.sh](https://github.com/tw93/Mole/blob/e6b990998c0d0bbcba4e0fcaa8e7b77e0e327c22/lib/clean/user.sh#L367-L407)). Mole hard-codes no age gate for installers, so JunkFinder's threshold is a design choice.

**The never-junk set is broad.** It covers Mail, Messages, Photos, Notes and Voice Memos libraries; iCloud `Mobile Documents` and `CloudStorage`, where "a local delete can propagate to other devices"; Keychains and credentials; `Group Containers`; `Application Support` and `Containers/<id>` as wholes ("a full sandboxed app home"); large `.db`/`.sqlite` files; and the XDG roots `~/.cache`, `~/.config` and `~/.local` as wholes ([mole.fit](https://mole.fit/blog/what-mac-cleaners-should-never-delete.md); [Mole SECURITY_AUDIT](https://github.com/tw93/Mole/blob/e6b990998c0d0bbcba4e0fcaa8e7b77e0e327c22/SECURITY_AUDIT.md)). iOS backups are a special case. Apple says "after you delete a backup, you can't recover it" and routes deletion through Finder's Manage Backups ([Apple](https://support.apple.com/108809)). JunkFinder can show their size and date, but only as Review. Language-file (`.lproj`) stripping, a CleanMyMac staple, does not belong in a home-folder scanner. Those files live inside signed app bundles, and changing them breaks the code signature ([Apple Developer Forums](https://developer.apple.com/forums/thread/706379); [Eclectic Light](https://eclecticlight.co/2020/11/03/code-signatures-3-fixing-signature-problems/)).

## totalFileAllocatedSize is the right number, but clones and links still lie

Apple DTS is explicit: use `fileSize` for logical size and `fileAllocatedSize` for size on disk, and "you shouldn't do that rounding yourself", because the allocated keys handle sparse files, forks, xattrs and small-file edge cases ([Apple Developer Forums 852593](https://developer.apple.com/forums/thread/852593?answerId=910847022)). A local test during this research on macOS 15.8.1 (recorded in the research notes, with no public URL) confirmed that `fileAllocatedSize` and `totalFileAllocatedSize` matched `du -k` exactly in every case: a 100 MiB sparse file with 1 MiB written reported 1,048,576 bytes; a `ditto --hfsCompression` file with 20 MB logical size reported 159,744 bytes; and a 1-byte file reported 4,096 bytes. The most striking real case was Docker Desktop's `Docker.raw`: **64 GB logical, about 350 MB allocated**. Spotlight's `kMDItemFSSize` reported 63,999,836,160 while `kMDItemPhysicalSize` reported 364,580,864 on the same machine. A big-files scanner that sums logical size gets this badly wrong. The same rule covers iCloud: once a file is evicted it becomes dataless, logical size stays the same, and an evicted folder's on-disk size "falls to less than 100 KB" ([Eclectic Light](https://eclecticlight.co/2023/10/29/last-week-on-my-mac-dataless-files-arrive/)). Allocated size alone keeps dataless files out of the big & stale list.

Neither size key notices **APFS clones**. In the local test, an original and its `cp -c` clone each reported the full 20 MiB. Finder's "on disk" figure is just as wrong: a cloned 107 GB VM showed about 54 GB per copy while the clone's real extra use was about 0.74 GB ([Eclectic Light, Sept 2026](https://eclecticlight.co/2026/09/05/when-the-finders-size-on-disk-is-misleading/)). Clones can be detected. `mayShareFileContentKey == true` plus an equal `fileContentIdentifierKey` marks pure clones. A partially overwritten clone gets a new content identifier but keeps `mayShare == true`, so content-ID grouping misses partial clones. getattrlist's `ATTR_CMNEXT_PRIVATESIZE` returns "the number of bytes … which would be freed immediately if the file were deleted" ([man getattrlist](https://leancrew.com/all-this/man/man2/getattrlist.html)). It has two traps, both seen in the local test and consistent with a third-party gist ([dreness](https://gist.github.com/dreness/08213395aef006720bd1fd9022d2a86e)). It returns **0 for both** the original and the clone, so summing it across a selection under-counts. And it returns 0 for decmpfs-compressed files that are not clones at all. So call it only when `mayShare` is true, and report a range: "frees ≥ private size, ≤ allocated size". DaisyDisk, the most careful commercial tool, counts full clones once, admits that partial clones "cannot be properly accounted for", and needs macOS 14+ for clone detection ([DaisyDisk](https://daisydiskapp.com/guide/hard-links)).

**Hard links** are simpler. They share an inode, while clones get distinct inodes ([Eclectic Light](https://eclecticlight.co/2025/05/13/how-to-tell-the-difference-between-copies-clone-files-and-hard-links/)). `du`, ncdu and DaisyDisk all count the first link and give the rest zero size ([DaisyDisk](https://daisydiskapp.com/guide/hard-links); [ncdu](https://manpages.org/ncdu)). Track (device, inode) only when `linkCount > 1`, which keeps the set small. dumac's global inode set cost about 1.5% of runtime ([healeycodes](https://healeycodes.com/maybe-the-fastest-disk-usage-program-on-macos)). Check `fileIdentifierKey` before comparing content IDs, because hard links also share a content ID. **Snapshots** add one more gap. PRIVATESIZE's definition excludes bytes "trapped inside a clone or snapshot", so a file pinned by a local Time Machine snapshot frees nothing until the snapshot goes. And there is no public per-file API for purgeable state ([Eclectic Light](https://eclecticlight.co/2023/04/15/what-is-purgeable-disk-space/)). JunkFinder should total "allocated bytes of matched items" and never promise that "Available" will rise by that amount. The volume keys do work in a CLI. The local test read 21.0 GB available and 27.8 GB "available for important usage", where the gap is purgeable space. They make a useful labelled footer, not a junk figure ([Apple](https://developer.apple.com/tutorials/data/documentation/foundation/checking-volume-storage-capacity.json)).

**Dates are where naive scanners go most wrong.** Apple's APFS reference says that without `STRICTATIME`, access time is updated on read "only if its value is prior to the timestamp stored in the mod_time field" ([Eclectic Light, Oct 2025](https://eclecticlight.co/2025/10/24/be-careful-when-interpreting-apfs-timestamps/)). The local test found that the Data volume is mounted without `strictatime`. A second and third `cat` left atime unchanged, so atime records only the first read after the last write. Backups and indexers can bump it, and QuickLook or Get Info can update it too. `kMDItemLastUsedDate` is written by LaunchServices and Finder opens, not by CLI reads. In the local test, **0 of the 25 files over 100 MB in `~`** had a last-used date, and a 2016 report put general coverage at about 10% of files ([cocoa-dev](https://lists.apple.com/archives/cocoa-dev/2016/Mar/msg00180.html)). The reliable signals are `contentModificationDateKey` and, for a folder, the newest modification date of any descendant, because a directory's own mtime changes only when entries are added, removed or renamed. In Downloads, `addedToDirectoryDateKey` records when the item arrived. Apple notes it behaves inconsistently on hard-linked items and isn't supported on all volumes. Treat last-used as an optional extra, and treat its absence as "unknown", never as "unused".

**Spotlight can enrich results, but it can't find junk.** NSMetadataQuery works in a CLI if it is started on the main thread with the main run loop spinning. The local test gathered 25 results in 0.10 s ([Apple](https://developer.apple.com/documentation/foundation/nsmetadataquery/start().md)). But `~/Library/Caches`, `~/.npm` and `~/.cache` had **zero indexed files** locally, hidden directories are not indexed by default, `kMDItemFSSize` is logical size, and hard links appear only once. Most developer junk is therefore invisible to it. A single report also says Spotlight ignores privacy exclusions on Tahoe ([Apple Forums 845516](https://developer.apple.com/forums/thread/845516)). JunkFinder needs a filesystem walk either way.

## macOS privacy hides Trash, Mail and Safari from a CLI without a word

TCC blocks *listing* of protected folders, not `stat`. In the local test with no FDA, listing `~/.Trash`, `~/Library/Mail`, `~/Library/Messages`, `~/Library/Safari`, `~/Library/Cookies` and the user TCC directory all failed with **`EPERM` (errno 1), not `EACCES`**, while `lstat` on the same directories succeeded. Mole's source records the same trap: "stat and -r both succeed under that block" ([Mole user.sh](https://github.com/tw93/Mole/blob/e6b990998c0d0bbcba4e0fcaa8e7b77e0e327c22/lib/clean/user.sh#L41-L60)). Swift's enumerator called its errorHandler once, with the root URL and `NSCocoaErrorDomain` 257 (`NSFileReadNoPermissionError`) wrapping POSIX 1. Returning `true` produced zero items, no crash and **no prompt**. A naive scanner reports Trash as 0 bytes and is wrong without ever knowing it. Apple keeps no complete, current list of protected folders ([Eclectic Light, Apr 2026](https://eclecticlight.co/2026/04/07/privacy-protected-folders/)). In practice there are four groups:

1. **Prompting "Files & Folders" locations**: Desktop, Documents, Downloads, iCloud Drive, third-party cloud storage, network volumes and removable volumes.
2. **FDA-only locations that fail silently**: Mail, Messages, Safari, Cookies, Calendars, AddressBook, CallHistory, Suggestions, IdentityServices, the TCC database, `.Trash`, and Apple app containers such as `com.apple.mail` ([Retrospect](https://docs.retrospect.com/docs/macos-sequoia-application-data-privacy-full-disk-access)).
3. **"Data from other apps"**: other apps' `~/Library/Containers` since Sonoma, extended to `~/Library/Group Containers` in Sequoia ([Eclectic Light](https://eclecticlight.co/2024/08/05/what-are-all-those-containers/); [Apple Forums 756701](https://developer.apple.com/forums/thread/756701)).
4. **Data Vaults**, which "being root won't give you access, nor will enabling FDA" ([Apple Forums 114452](https://developer.apple.com/forums/thread/114452)).

Container protection also costs time. DaisyDisk and ncdu scans of `~/Library/Containers` slowed from about 5 s to about 20 s on Sonoma because of per-folder security checks ([MacRumors](https://forums.macrumors.com/threads/daisydisk-very-slow-to-scan-in-sonoma.2406837/page-2)).

**The permission belongs to the terminal, not to JunkFinder.** TCC credits access to the *responsible process*, the GUI app at the top of the launch chain. iTerm2 is "responsible for MyApp" when MyApp is launched from it, and the same holds for VS Code's Electron binary ([Qt blog](https://www.qt.io/blog/the-curious-case-of-the-responsible-process)). Prompts name the terminal, and FDA has to be granted to the terminal. Granting it gives FDA to every command run in that terminal, which Oakley warns makes ClickFix-style attacks easier ([Eclectic Light](https://eclecticlight.co/2026/04/07/privacy-protected-folders/)). Hosts that disclaim responsibility behave differently. When Claude Code is hosted by Claude Desktop through its `disclaimer` helper, it gets `EPERM` on Desktop, Documents and Downloads with **no consent prompt** ([claudeissues #90687](https://claudeissues.com/issue/90687-macos-tcc-protected-folders-unreadable-no-consent-prompt-no-remediation-in-the-e)). Under launchd or cron no GUI app is responsible, and an unsigned binary that `swift build` rebuilds each time makes a poor TCC identity ([Apple Forums 661178](https://developer.apple.com/forums/thread/661178)). Scheduled scans of protected paths should be documented as unsupported.

**No API detects FDA.** Quinn of Apple DTS advises against probing TCC.db: "the location and permissions of the TCC database is not considered API" ([Apple Forums 114452](https://developer.apple.com/forums/thread/114452)). An August 2026 thread reports that the TCC.db probe now gives false negatives on macOS 27 even with FDA granted. Kevin Elliott of DTS says "there isn't currently a 'general' solution". He recommends spot-checking the locations you actually need and warning that "FDA might be the issue" ([Apple Forums 841091](https://developer.apple.com/forums/thread/841091)). For JunkFinder that means trying to list `~/Library/Safari`, then `~/Library/Mail`, then `~/.Trash`. These folders are FDA-only, nearly always present, and never prompt (verified locally for all three). The deep link `x-apple.systempreferences:com.apple.preference.security?Privacy_AllFiles` is reported to work on Sonoma, but nobody has confirmed it on 15 or 26 ([Keyboard Maestro forum](https://forum.keyboardmaestro.com/t/which-action-do-you-use-to-access-mac-os-settings/40680)). The manual path, System Settings › Privacy & Security › Full Disk Access, has stayed the same through Tahoe. Mole's help tells users to relaunch the terminal after granting FDA ([mole.fit/help](https://mole.fit/help)). Mole itself works without FDA, and its own estimate is that FDA adds only about 2–5 GB of reclaimable space. That supports a default no-FDA scan with an opt-in deeper scan. A known failure mode in cleaners is repeated permission prompts, which one project fixed with a one-time FDA flow ([desktop-cleaner PR #6](https://github.com/fawad-khalil/desktop-cleaner/pull/6)).

One conflict between the categories and the privacy rules has to be settled. The TCC notes suggest skipping `~/Downloads` to avoid prompts, but category 3 exists to scan it. The right compromise is to read Downloads, since the user asked for that category, and to read only Downloads among the three prompting folders. The first scan from a fresh terminal may then show one dialog naming the terminal app. If the user declines, the installer category has to say "Downloads not readable" rather than "nothing found". Desktop and Documents stay out of the default walk because no rule needs them. They become an opt-in flag that widens the big & stale search.

## Skipping the right trees beats scanning faster

**Dataless directories are the worst trap.** Apple's TN3150 says that "enumerating a directory's contents" and `fileExists(atPath:)` can trigger materialization, that `stat` and `getattrlist` "trigger the materialization of any intermediate folders in the file's path, if they themselves are dataless", and that the symptoms include hangs and `ETIMEDOUT` ([Apple TN3150](https://developer.apple.com/tutorials/data/documentation/technotes/tn3150-getting-ready-for-data-less-files.json)). The fix is one call at startup: `setiopolicy_np(IOPOL_TYPE_VFS_MATERIALIZE_DATALESS_FILES, IOPOL_SCOPE_PROCESS, IOPOL_MATERIALIZE_DATALESS_FILES_OFF)`. After that, any `EDEADLK` means "dataless, skip it". Use process scope, because Swift concurrency moves work across threads. Detection uses `SF_DATALESS` in `st_flags`. In Mole's case a Google Drive root used up the whole scan budget, and Mole now prunes `-flags +dataless` ([Mole project.sh](https://github.com/tw93/Mole/blob/e6b990998c0d0bbcba4e0fcaa8e7b77e0e327c22/lib/clean/project.sh#L640-L680)). Reading file content is what reliably starts a download ([icloud-pull](https://github.com/hyper0x/icloud-pull)). That puts the zip-content check in tension with a "metadata only" rule. JunkFinder should open a `.zip` only after confirming it is local (not dataless, and allocated size close to logical size), and only to read the central directory.

**Volumes, firmlinks and links need device and inode checks, not path checks.** `/Users` reaches the Data volume through a firmlink, and firmlinks don't change `st_dev`. Scanning from `~` and nowhere else avoids the familiar double count of "Macintosh HD – Data" ([Apple Community](https://discussions.apple.com/thread/251859112)). Mount points inside home do exist. On the research machine, `~/OrbStack` is a network or FUSE mount. The URL enumerator has no "stay on one filesystem" option, so compare `volumeIdentifierKey` (or `st_dev`) with the root's, and call `skipDescendants()` when they differ. The local test showed the URL enumerator **never follows symlinks**: directory symlinks come back as items with `isDirectory == false`. But an enumerator *rooted* at a symlink fails with ENOTDIR, so resolve `~` with `resolvingSymlinksInPath()` first. A `chmod 000` directory is yielded, then reported as Cocoa 257 / POSIX 13 (EACCES). That keeps it distinguishable from TCC's EPERM. Nesting is the last double-count. Once a path matches a rule (`node_modules`, `target`, DerivedData), JunkFinder sizes that subtree without testing its descendants against other rules. Otherwise `node_modules/x/node_modules` and `target/debug/build/*/out` get counted twice. Packages such as `.app`, `.xcarchive` and `.photoslibrary` are single opaque units. `.skipsPackageDescendants` yields the bundle but not its contents, so measuring a bundle takes a separate sub-walk.

**The speed evidence conflicts, and both sides point to a simple v1.** dumac's warm benchmark of 409,500 files clocked `du` at 3.33 s and a parallel `getattrlistbulk` walk (128 KB buffer, 64 concurrent tasks) at **521 ms**. A naive goroutine-per-file `lstat` walk was slower than `du` ([healeycodes](https://healeycodes.com/maybe-the-fastest-disk-usage-program-on-macos)). Apple DTS (Kevin Elliott) says the URL-based FileManager APIs with prefetched keys "are just as fast, far easier to use and … more likely to correctly handle weird edge cases". He measured fts as only about 0.2 s faster over 350,000 files. He calls the `atPath:` variants "FAR slower" and recommends flattening recursion into a queue, after a macOS 15 `getattrlistbulk` loop on SMB ([Apple Forums 766035](https://developer.apple.com/forums/thread/766035)). Thomas Tempelmann's 2019 tests found fts fastest in most cases and APFS searches 5–6x slower than HFS+ ([Michael Tsai](https://mjtsai.com/blog/2019/04/22/performance-considerations-when-reading-directories-on-macos)). No source has a cold-cache or 2024–2026 head-to-head benchmark on a real home folder. JunkFinder's workload is the deciding factor. It skips cloud, Photos, Mail, containers and VM images, and it stops descending at each match. So it walks a fraction of the home folder, and a synchronous URL enumerator should be fast enough. Move to a queue-based `getattrlistbulk` walker only if measurement shows it is needed, and add a walker protocol then, not before. Keeping v1 synchronous also sidesteps Swift 6 strict-concurrency friction. Blocking syscalls inside the cooperative pool can starve it, and a single-threaded top-level loop has no data races to annotate. Memory matters more than raw speed. Don't keep a tree of millions of `URL`s. Aggregate per matched root and keep a top-N list.

### FDA and permission UX

The default run uses no FDA, shows no prompts except the one possible Downloads dialog, and makes no claim it can't back up. In the errorHandler, classify each failure and always return `true`. Cocoa 257 with an underlying POSIX `EPERM` means "protected by macOS privacy". POSIX `EACCES` means "no POSIX permission (owner)". `EDEADLK` means "cloud-only". Collect these into a deduplicated list of top-level paths, and print one summary line at the end, never one line per file: "Skipped 4 protected locations (Trash, Mail Downloads…); sizes are incomplete. Run `junk --check-access`." `--check-access` runs the three-path probe, names the likely responsible app from `TERM_PROGRAM` (`Apple_Terminal`, `iTerm.app`, `vscode`; this is a heuristic, not authoritative), and prints the manual steps: System Settings › Privacy & Security › Full Disk Access, add the terminal, then **quit and reopen it**. It should also tell users to revoke FDA afterwards, rather than recommend leaving Terminal with permanent FDA. When the probe passes, rules C6 and C7 turn on automatically. When JunkFinder detects that it is not under an interactive terminal (no TTY, launchd), it warns that prompts can't appear and protected paths will simply be skipped. If Downloads returns EPERM, the installer section prints "Downloads not readable — allow access for <terminal> in Privacy & Security › Files and Folders", not an empty list.

### Output caveats

Each report should state, once, in a footer:

- Sizes are allocated bytes, so sparse VM disks and compressed or cloud-only files are counted at what they actually occupy.
- Hard links are counted once. Clones are counted at full size unless marked "clone: frees X–Y".
- Space held by local Time Machine snapshots is not freed until the snapshot expires (`tmutil listlocalsnapshots /`).
- "Available" in Finder or System Settings will not rise one-for-one, and those panes use volume-level, partly purgeable-adjusted figures that won't match JunkFinder's totals.
- Caches regenerate, and macOS purges many of them itself.
- The list of skipped areas means totals are a lower bound.

Junk and Review get separate totals, and only the Junk total is described as "reclaimable". Each finding shows path, allocated size, age basis ("modified 214 d ago", "added 95 d ago", "last opened: unknown") and the owner command or consequence line.

## Conclusion

Measuring correctly turns out to be most of the safety work. One unit, allocated bytes, removes the three largest false positives that a naive scanner reports: sparse VM disks, compressed files and evicted cloud files. One habit, deciding what not to walk, avoids TCC prompts, File Provider downloads, slow container checks and double counting at mounts in the same move. What remains cannot be made exact. Clone sharing, snapshot pinning and purgeable accounting have no complete public per-file API. An honest tool reports a lower-bound total and a range for clones, and says why.

The deeper design point is that a list-only tool carries real risk, because its label works as an instruction. The best cleaners already treat "large and old" and "safe to delete" as separate verdicts. Mole's review tier and CleanMyMac's refusal to pre-select the newest backup both show this. JunkFinder can go a step further than either by printing the owning tool's own cleanup command and a one-line consequence for every Review item. That is something a list-only design can do better than a deleting one.
